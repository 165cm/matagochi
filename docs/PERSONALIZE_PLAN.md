## 1. 実現する価値
「あなたの好みと、好きな動画から。買い物のペースに合う夜ごはんへ。」

1人・2人暮らしを中心に、次の循環を実現する。
**話を聞く → 好みを確認 → 動画レシピを選ぶ → 献立と買い物 → 動画を見ながら調理 → 記録と評価 → 理解を更新**

初回診断は短さだけを追求しない。「回答を理解し、聞き返し、献立を修正してくれる」という共同作業を価値にする。
質問や待ち時間を無意味に増やしたり、実行していないAI処理を演出したりしない。

## 2. 確定方針と未確定事項
### 確定した方向
- 初回は深いパーソナライズ。固定分類だけで終わらず、回答理由を聞いて確認する。
- 動画の自動取り込みの主対象はYouTubeのみ。
- 初日から使える動画レシピの品ぞろえと、新作が追加される仕組みを用意する。
- 投稿者の利益・出典・掲載管理・利用条件を尊重する。
- 過去の献立・個人別評価・好みの言語化・変化を見られるようにする。
- 無料は「今夜の1日分」、プラスは「3日／3日＋3日／5日」の献立と買い物ペース。
- プラスには2〜4週間の無料体験を設ける。
- 実装は既存機能を活かして段階的に進める。コード全面置換やフレームワーク移行は本件の目的ではない。

### 2026-10-01 にユーザーが決めたこと（PR 4・PR 7）
- **基本のレシピは YouTube から**集める
- **投稿者の同意がない動画**は「新着」として**28日間**、ランダムに見せる（今の新着の28日と同じ）。見せた中から利用者が献立に入れたものは、**その人が自分の意思で保存したもの**として残す（どこに残すかの細かい点は確認中：下の「確認中」）
- **品数**は多ければよいのではなく、**献立に入れられた割合（採用率）が基準を満たす料理だけを残す**。基準の数はデータを見て決める
- **費用**：収益の1％以内に収まるなら、まずは費用を気にせず集める。負担が大きい時は制限する
- **当面の目標**：条件を満たしたうえで、**4週間、同じ料理を出さずに献立を出せる量**（棚卸しの「2週間ぶん」の目安を「4週間ぶん」に上げる）
- **お試し（PR 7）**：お金を払うのは献立を考える人なので**本人（アカウント）単位**。期間は**2週間**（以前の仮案の28日から変更）。**続けない（キャンセル）を選んだ人には、追加で最大2週間延ばせる**。課金への移行率などを見て調整する
- 追加で決めたこと（同日）：
  - ① 新着から献立に入れられた料理は、その人の保存に加えて、**みんなに見せる一覧（みんなの定番）にも残す**。ただし YouTube の決まりと #103 の後片付けはそのまま守る：説明文・チャンネル名は30日以内に確かめ直す／削除・非公開・埋め込み不可になったら一覧から外す／投稿者が止めた動画・チャンネルは出さない／出典（投稿者名・元の動画）を必ず出す。同意のない投稿者の料理を長く見せることになるので、よく採用される動画の投稿者には、参加の申請（同意）をお願いする導線を運営側に用意する
  - ② 収益がまだない間（β版）のレシピ集めの費用は**月1,000円まで**。届いたらその月は集めるのを止める。まず1品あたりの原価を測る
  - ③ 延長は、2週間のお試しの終わりに「続けない」を選んだ人に**1回だけ**「あと最大2週間ためす」を提案する。カード登録なし・自動で課金しないのは同じ
  - ④ お金を払った本人のプラスは、**同じ家族の合言葉で同期している端末でも使える**（見ているだけの人は今と同じ見るだけ）

### 実装用の仮案
- 診断：15〜25程度の短いやり取りを目安に分岐。全員に同数を要求しない。
- 無料体験：~~28日を開発環境の初期値~~ → 2026-10-01 に**14日（2週間）**に決定。期間は設定で変えられる構造にする。
- 体験：カード登録なし、自動課金なし。終了後は無料へ。課金への切替は本人の明示操作。
- 基本動画：100〜150品程度を将来の編集目安にする。実装完了条件として無断大量収集しない。
- 画面例の月480円／年3,900円は未決定の仮価格。既存の料金を勝手に置換しない。
- 新規AI解析の無料・有料・体験中の回数上限は、原価計測後に決定する。設定可能な制限機構を先に作る。

### 今回承認されていないこと

## 4. 初回診断：共同で「わが家のごはん方針」を作る
### 4.1 会話の構造
1. 暮らしと困りごと：人数、帰宅時間、誰が作るか、夕食の何が大変か。
2. 好み：写真、味付け、食感、よく食べたい料理、好きなYouTube動画。
3. 実行負担：時間、包丁、洗い物、待ち時間、器具、常備品。
4. 深掘り：好きなのに作らない理由、平日と休日の違い、同居人との違い。
5. 献立案への反応：「これだと作れそう？」「変えるならどこ？」。
6. 編集できる方針を提示し、本人の確認で保存。

例：
「魚は好きだけど作らない」
→「骨・片付け・焼き加減なら、どれが気になりますか？」
→「片付け」
→「魚を減らすより、ホイル蒸しを候補に入れてみます。合っていますか？」

### 4.2 操作要件
- 選択肢中心＋任意自由記述。「わからない」「後で」「戻る」「保存して閉じる」。
- 回答に応じて追質問を変える。既に回答した内容は再質問しない。
- 途中まででも今夜の候補へ進める。既存ユーザーへ強制的に初回診断を再実行しない。
- 診断結果は無料。最初の具体的な料理と、その推薦理由まで表示する。
- 2人目は後から参加できる。本人不在でAIが相手の好みを確定しない。
- 回答を直したら、関連する解釈と献立案も更新する。
- AIを利用している箇所と、回答を送信する目的を分かるようにする。自由記述を無関係な集計に転用しない。
- タイマーだけで100%になる現行演出は、実処理に対応した状態表示へ変更する。

### 4.3 AIとルールの責任分担
AI：自由記述の構造化、追加質問、回答要約、根拠に基づく提案理由。
通常のコード：食材制限・器具・時間・人数・禁止条件の検証、候補の適合性、保存・権限。
アレルギーと単なる苦手を区別。AIの推測で制限を解除しない。
情報が不明な料理を「制限に適合する」と断定しない。代替食材も確認済み条件で扱う。
AI出力は構造検証し、許可した操作と項目だけ使う。自由記述や動画説明文をシステム命令として実行しない。
通信失敗・不正なJSON・タイムアウト時は入力を失わず、定型質問と既存の条件ベース提案へ戻れる。
AIサービスアカウント・APIキーはサーバー側のみ。入力全文を通常ログに残さない。
会話のたびに全履歴を無制限送信せず、必要な文脈と確認済みプロファイルを使う。予算・回数・タイムアウトを管理する。

## 5. 好みのデータと変化
既存stateを破壊せず、版付きの追加データとして設計する。以下は概念名であり、既存名を置き換える指示ではない。

- 回答：対象者、質問ID、値、記録時刻。
- 解釈：嗜好／生活条件／食材制限の区別、根拠ID、確認済み／推測／未確認。
- 方針のスナップショット：版、時刻、当時の内容、更新理由。
- 評価：料理・人物ごとの有効な評価。未回答と低評価を区別。
- 推薦理由：どの明示条件・評価を使ったか追える参照。

「本人が言ったこと」「記録からの傾向」「次に試す提案」を分離する。
傾向には対象期間と件数を添える。証拠のない成長率や精密な好みスコアを生成しない。
「少し違う」から修正でき、古い推測が次回また復活しないようにする。
料理の評価が変わったことと、忙しさ・季節など状況が変わったことを混同しない。
個人の詳細な診断回答を、既存の家族同期へ無条件に追加しない。共有範囲は明示選択し、サーバーAI処理への送信と家族共有は別扱いにする。
データの削除・書き出し・移行を設計し、バックアップに含まれる情報も説明する。

## 6. YouTube動画の取り込み
### 必須の利用者フロー
共有またはURL貼付 → メタデータ取得 → 材料・手順のAI下書き → 元動画と見比べて確認 → 保存 → 今日／今週へ追加。
人数不明は不明のまま表示し、勝手に1人分へ換算しない。
元動画ID、URL、作者、元人数、材料、手順、任意の時刻、取得・確認状態を保持。
再生は公式埋め込み。閲覧自体をプラス限定にしない。
解析上限に達してもURL保存・保存済み動画の再生・手入力は可能にする。
削除・非公開・地域制限・埋め込み不可・解析失敗・不十分な材料を区別して扱う。
AI解析可能な公開動画と、URLを保存するだけの動画を区別する。
動画の複製保存や非公式字幕スクレイピングを前提としない。
Instagram/TikTokの新規自動解析は今回対象外。既存の保存データと元URLは壊さない。

## 7. 基本カタログと日々の更新
### 7.1 3つの保管領域を区別
- 確認済みの基本動画レシピ
- 新着の候補・下書き・確認待ち
- 個人が取り込んだ動画レシピ
個人の取り込み結果を、自動的に公共のおすすめ一覧へ昇格させない。既存の共通キャッシュとも公開配信権限を区別する。

### 7.2 品ぞろえ
100〜150品は将来目安。テストは許諾済み素材または架空fixtureで可能にする。
主材料、味付け、10/20/30分、器具、調理負担、元人数等で不足を確認する。
解析しやすさだけで順位を決めず、狙う利用者の条件に対して候補が何品残るか検証する。
全ての食材制限に対応できると表示しない。候補不足時は条件を勝手に緩めない。

### 7.3 収集パイプライン
登録チャンネルの新着検知
→ IDで重複排除
→ 公開・埋め込み・利用範囲確認
→ 解析予算予約
→ 下書き
→ 品質／必要な権利確認
→ 公開可能なカタログへ
→ 定期更新・非掲載化。

最初は認証付きの定期実行＋公式APIでよい。WebSub導入時は購読更新、重複通知、再試行、検証を扱う。
YouTube APIの取得枠とAI費用は別に監視する。解析回数だけで総費用が管理できるとみなさない。
ユーザー取り込み用の予算を自動収集が使い切らない。
「今週10品」の表示上限と、日々の収集処理を分離する。毎日必ず新着があるとは保証しない。
trends/popular等のGETは原則、確認済みデータを読み出すだけにし、閲覧リクエストで新規の有料AI処理を起動しない。
状態と再試行・排他・期限・エラーが追えるようにし、失敗を成功扱いするワークフローにしない。

## 8. 投稿者との関係と利用条件
### 公開前に必要な設計
- 投稿者名・元動画・チャンネルへの導線を維持。
- 「YouTubeの再生数・収益が必ず増える」という現行の断定を修正。
- 登録・視聴・高評価をチケット等の報酬条件にしない。
- 動画・広告・リンクを隠さない。自動再生・ループを視聴数稼ぎに使わない。
- 基本カタログの中核は協力投稿者から。材料表・人数・手順を直接提供してもらえる構造も設計する。
- 投稿者の許可とYouTube利用条件は別。許可だけで全用途が認められたとは扱わない。
- AI抽出・保存・要約・人数換算・一般公開の範囲を、同意情報として別々に管理。
- 公開ページに「参加申請」「修正依頼」「掲載停止」を用意。申請は自動的に提携済みとしない。
- 第三者からの停止申請と、確認済み投稿者の管理権限を分離。申し立ては一時対応・審査・復旧を追跡する。
- 確認済み投稿者が他人のチャンネルを管理できないようサーバー側で所有・権限を検証。
- アプリ内保存・献立採用・調理記録・外部リンククリックは、YouTube公式の再生・登録数と区別して報告。
- 個人の食材制限・会話・家族評価を投稿者に開示しない。少数集計からの個人特定にも配慮する。

### 保存期間と取り消し
YouTube API由来メタデータ、作者から直接提供された情報、個人の調理記録を区別する。
対象APIデータの更新・削除を定期処理で保証し、読み出されないデータも残し続けない。
タイトル・サムネイル・作者・公開状態・埋め込み可否等の対象項目を列挙する。端末キャッシュ・共通カタログ・版履歴も確認。
掲載停止・削除時、公開推薦と解析素材の取り扱いを適切に停止する。利用者が自分で書いた調理メモまで一律に消さない。
AIによる派生データは無条件に永久保存してよいと仮定しない。許諾未確定時は公開配信を止める状態を用意する。
公式資料の技術対応を、法的な包括許可と読み替えない。条件判断が未完了でも、管理画面・テスト・無効化機構は進める。

## 9. 献立と買い物
無料：毎日の今夜1品。候補変更を1日1回に制限する意味ではない。
プラス：
- 3日：選んだ3回分。
- 3日＋3日：前半と後半、原則週2回の買い物。残り1日は自由。
- 5日：平日など選んだ5回分をまとめる。残り2日は自由。
週の始まり・買い物曜日・自炊する日を選べる。月曜固定にしない。
後半は前半の実績と利用者が確認した残り食材で組み直せる。使ったはずとAIだけで在庫を断定しない。
購入済みチェックを維持し、入れ替えで増えた／不要になった品を示す。
5日分のまとめ買いでも保存可能日数を推測で保証しない。確認済みの保存情報を使い、不明なら後半の買い足しへ。
人数変更・お休み・翌日へ移動・固定した料理を扱い、確定済み献立を新着で勝手に置換しない。
3/7日形式など既存データは読み込めるよう移行し、旧クライアントとAPIの互換性を保つ。

## 10. 記録画面と利用後の理解更新
主タブ：今日／買い物／レシピ／記録。
記録内：カレンダー／定番／わかってきた好み。
料理写真、作った日、人数、個人別評価、味付けメモ、元動画、作った回数を表示。
「もう一度、献立に入れる」を用意。
評価は食後毎回要求せず、献立の一巡後にまとめて任意回答。
初回の方針と最近の記録の差分を根拠つきで表示し、本人が採用・修正できる。
例：「魚料理3品のうち2品が『また食べたい』。蒸し料理を増やしますか？」。
料理の嗜好を優劣で評価しない。「成長」は実際に作れた料理・増えた定番・本人の感想に基づく。
無料復帰後も保存済み記録の閲覧・再利用・書き出しができる。

## 11. 試用・課金・計測
本番では現行のベータ無料状態を維持。新しい制限は開発フラグとモックで検証する。
28日/14日を設定可能にし、開始・終了時刻はサーバーで管理する。端末時計・再読み込みで延長されない。
開始は本人の操作。リクエスト再送・複数端末・同時開始に対して一度だけ成立する。
復元可能な利用主体（アカウント／世帯）の識別と認可を設計する。信頼できないX-Householdだけで有料権限を付与しない。
正確な実決済・請求・価格変更は後続の別PRと承認対象。ブラウザ内フラグを本番の購入証明にしない。
AI診断・動画・画像解析の利用枠と、献立提案の回数を混同しない。
上限・残量・失敗時の扱いを利用前に示す。成功結果を再利用できる場合は無用な再解析をしない。

計測：
診断開始/完了、追質問への回答、本人による理解修正、献立確定、動画取り込み成功/要修正、買い物利用、調理記録、過去の記録からの再調理、試用開始、継続。
料理名・自由記述・食材制限を分析イベントへ送らない。
14日対28日は同じ開始後56日で、継続と変動費込みの収益を比較できるよう設計する。初期段階で自動実験を本番開始しない。

## 12. 優先して直す既存問題
1. 個人別評価：料理ごとに最新の1記録を選ぶだけでは別人物の有効評価を落とし得る。料理×人物単位の最新有効評価へ。
2. 発見API：表示取得から新規解析やキャッチ生成が走る結合を解消。
3. API情報の更新：閲覧時の説明文・チャンネル名更新だけに依存しない。
4. 掲載停止：未確認の申請者がチャンネル単位の停止を確定できる構造を見直す。
5. 投稿者向け説明：再生数・収益への断定を修正。
6. パーソナライズ：時間経過だけの進捗と、回答の実際の反映を区別。
7. 収集：週10品充足で新着更新が止まる構造を、表示枠と収集枠に分ける。
本番への危険度と依存関係に応じ、小さな修正PRに分けてよい。

## 14. 受け入れ条件と必要なテスト
### 保存・互換
- 旧state・旧バックアップ・旧同期データを読み込み、料理・履歴・写真・買い物が失われない。
- 移行を複数回行っても重複しない。診断の途中終了・再読み込み・通信失敗から再開できる。
- 既存の保存キー、公開パス、deriveSyncRoomId、API互換を破壊しない。

### 診断と学習
- 同じ回答を繰り返し聞かず、理由によって次の質問と候補が変わる。
- 食材制限をAI出力で上書きしない。人数不明・未確認食材を誤って適合としない。
- 推測を修正するとプロフィールと次の提案へ反映される。
- 片方の新しい未回答記録で、もう片方の以前の評価を失わない。
- AIタイムアウト・不正出力・悪意ある自由記述を安全に扱える。

### 動画・収集・投稿者
- 同一動画への同時要求、重複通知、再試行で無用な二重解析を起こさない。
- 一覧GETだけで新規の有料AI処理が発生しない。
- 非公開化・埋め込み禁止・削除・掲載取り消しが推薦とキャッシュへ反映される。
- 未確認の許諾・投稿者を、公開可・本人確認済みにできない。
- 他人のチャンネルを修正・再掲載できない。
- 解析上限・YouTube API障害でユーザーの入力や既存レシピを失わない。

### 献立・体験
- 3＋3で6回分と前半/後半の買い物を正しく分ける。5日で5回分。休みを含む週も扱う。
- 予定変更や人数変更で必要量が変わり、購入済みを不必要に消さない。
- 候補不足時に禁止食材・時間・器具条件を黙って緩めない。
- 体験の開始・再送・複数端末・期限境界・無料復帰を検証。
- 無料復帰後も動画再生・保存済み献立・個人の記録・書き出しが使える。
