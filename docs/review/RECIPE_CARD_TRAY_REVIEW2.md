## 高（直すまで公開しない）

1. **触っていない「決めた・買った日」まで決め直してしまい、買い物リストに材料が戻る**（`daily-ui.js` 5971〜5975行 `life-tray-confirm-all`）
   確かめた：今日の料理を決めて買い物を済ませ（買う物0品）、トレイを開いて何も触らずに「この3日分で決定」→ 今日の料理は同じなのに更新日時が変わり、買う物に「ごはん・豚こま・キャベツ・しょうゆ」など今日の分が戻る。
   原因：`validated` の全部に `confirmDaily()` を呼ぶ。`confirmDaily` は新しい日時・買った印なしの枠を作る（#234 のレビューで分かった性質）。いつもの `life-confirm` は、まだ決めていない日（`d.candidate`）だけを決める。
   直し方：**下書きの料理が、開いた時と同じで、すでに決めてある日は飛ばす**（`trayDraft[date] === trayInitialDraft[date]` かつ `mealSlots[date].status === "confirmed"`）。回帰テストも（直す前のコードで落ちること）。

## 中

2. **決めてある日を空にして「決定」しても、その日は元の料理のまま**（5977〜5982行）：トレイでは空に見えるのに、献立には元の料理が決まったまま残る（確かめた）。空の日がある時は決定ボタンを出さない（全部そろった時だけ）か、空にした日を「未定」に戻すかを決める。おすすめは前者（終わりが見える・事故が少ない）。
3. **見るだけの家族の「作った」を止める変更が入っている**（`household.js` 196行：`life-cooked`・`life-record-past` を `VIEWER_BLOCKED` に追加）：トレイとは別の、今ある動きの変更。本番では見るだけの家族も「作った？」に答えられる作りなので、意図した変更かユーザーに確認が要る（意図していなければ外す）。
4. **栄養・塩分の方針をユーザーの判断なしに変えている**（`docs/PRODUCT.md`：「やらないこと」から栄養計算を外した）。前回のレビューの問い①（外す／残す）にまだ答えが出ていない。裏面の折りたたみの中だけ、という置き方は良い。残す場合の残り：
   - **だし・スープを「素（顆粒）」として数える**：鶏ガラスープ800ml・4人分 → 塩分 52.2g/人。水で溶いたスープ・だし汁は別の扱いにし、ありえない値（例：1人分10g超）は「不明」にする
   - 油のエネルギーを数えていない（キャベツ200g＋油大さじ1＋しょうゆ大さじ1・2人分 → 79kcal）
   - 表示の言葉「材料から推定（主菜1品）」は良い。出どころの「日本食品標準成分表」は、数え方が粗いうちは前面に出さない
5. **絵の方針もユーザーの判断待ち**（前回の問い②）：新着（YouTube）の「豚の生姜焼き」は、投稿者のサムネイルではなくアプリの生姜焼きの絵になる（`APPROVED_PARENT_ILLUSTRATION_RULES`）。同じ料理名の絵なので前回の「別の料理の絵」ではないが、投稿者の写真を出さないことになる。裏面には動画への入口がある。
6. **速さが docs の数字と合わない**（`docs/APP_MAP.md` §67-3「開く 約0.15秒・置く 約0.05秒」）：スマホ相当（4倍遅い設定）・400品で、開く 約0.66秒・置く 約0.59秒・献立の画面の描き直し 約0.27秒（本番は約0.18秒）。docs の数字はパソコンの速さだと思われる。測った条件を書くか、数字を直す。置くたびに候補の一覧を全部作り直しているのが主な原因。
7. **`state.planConfirmedAt` という新しい項目を足している**（5976行）：どこからも読まれていない。使わないなら足さない（`state` に項目を足す時は docs に）。
