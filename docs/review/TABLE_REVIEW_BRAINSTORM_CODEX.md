# わたしの食卓レビュー｜Codex ブレスト案

（2026-11-23。Codex の `codex/table-review` の回答を、ユーザーがチャットに貼った全文から写した）

## 1. ひとことで

「今年、もう一度食べたいのはこの一皿」。好きな一皿を自分で表紙に選び、その頃の食卓を小さな絵はがきにする。記録が一つでも完成する。

## 2. たたき台への評価

**残す**　①週は聞き慣れたレシートの期間にそろえる。②写真は端末内で扱い、共有前に完成画像を見せる。③見返した料理から「もう一度」を押して、次の献立に戻れるようにする。

**削る**　①ベスト3の固定枠。記録が少ないほど空欄が目立つ。②「あと何回で解放」。一枚ある人にその一枚を返したい。③初版の栄養・彩りパレット。レシピから食材の候補はわかるが、置き換えた材料、実際に食べた量、盛りつけの色はわからない。

**危ない**　①単位の混同。例えば同じ日に手入力で2皿、片方は確定献立にも載っていたら「記録2件・1日」。週レシートの cooked は記録日と調理済み献立日の和集合なので1になる。献立達成率が必要なら、分母は対象の確定・調理済み枠、分子はそのうち調理済みの枠だけにする。②新顔の誤認。「この端末に残る記録で初登場」に限定し、開始日以前の履歴も調べる。recipeId が違えば同じ料理の別レシピでも別件。「種類」と出すなら図鑑の同一カードにまとめられる範囲を明示する。③評価の時点。月画面は好意的な回答を足し、週レシートは現在の評価も参照する。過去期間には、その期間に作った記録だけを latestRatings に渡し、料理×人の最新回答を使う。未回答は分母から外す。後日編集された回答の当時の値は復元できない。

## 3. 期間ごとの設計

| 期間 | 主役 | 見せ方 |
|---|---|---|
| 1週 | もう一度食べたい一皿 | 既存レシートと同じ週（月〜木は先週、金〜日は今週）。日付と一皿を大きく。 |
| 4週 | 何度か登場したレシピ | 選んだ週の末日までの28日を4行にし、記録日にだけ小さな印。同じレシピが別の週にもあれば線で結ぶ。 |
| 3か月 | 食卓の移り変わり | 選んだ月までの暦月3枚。各月から一皿、空の月は省く。 |
| 半年 | 久しぶりに登場した一皿 | 暦月6か月。同じレシピを記録した二つの日付を並べる。一度ずつなら好きな一皿を選ぶ。 |
| 1年 | 「2026年のわたしの食卓」 | 1月〜12月の暦年。途中参加なら「11〜12月の記録から」と添え、選んだ一皿を年賀状のように飾る。 |

未来の日は集計せず、見出しに実際の対象日を表示する。月カレンダーは記録を探す場所として保ち、レビューを開いた先で期間を選ぶ。集計元は表示タイル（最大31件）でなく evaluations 全件。画面と同じ食事日のキーで絞り、デモ・無効日は期間内と過去履歴の両方から除く。同じ記録IDを二重に数えず、レシピを削除済みでも記録日と保存済み料理名は使える。IDが不明なら品数の推定には使わない。

## 4. 新しい項目のアイデア

| 表示案 | 使うデータと成立条件 |
|---|---|
| 「おかえり、肉じゃが」 | recipeId ごとの異なる cookedAt の日付。例えば前回の記録から28日以上なら二つの日付を並べる。空白期間に食べなかったとは言わない。 |
| 「火曜日によく登場」 | 同じレシピの記録日から曜日を求め、異なる3週以上で曜日が一致したら表示。 |
| 「キャベツの別の食べ方」 | 記録にひもづく別レシピ2件の材料名を Lifestyle.key で正規化。共通する生鮮食材と料理名を並べる。節約額や廃棄削減量には換算しない。 |
| 「ふたりが選んだ別々の一皿」 | familyRepeatCycles の期間内の回答から各人の「明日でも／毎週」を一皿ずつ。双方が回答したときだけ端末内で表示。 |
| 「冬から春へ、同じ一皿」 | 同一 recipeId の記録日が季節をまたぐ場合に月名を並べる。季節は日付から読めるが、産地や旬の証明には使わない。 |
| 「あの日の写真便り」 | 期間の端と端で読める記録写真を各1枚。1枚なら全面に。古い写真の参照が解決できないときはイラストを選ぶ。 |

## 5. SNS 画像の設計

上から「年・期間」→「自分で選んだ一皿」の絵または写真→「記録した○日」と任意の料理名→余白によはく1匹、リピごちのロゴと短い入口。まず9:16を1枚。本人が一皿を選んだ理由をSNSの投稿欄に書ける余白を残す。標準はイラスト、料理名オフ。家族名・メモ・個別評価・撮影日時は描画しない。写真に写った人や室内は自動で隠れないので、写真を選んだ後も絵に戻せるようにする。

Canvasには同梱の絵と読み込みに成功した端末写真だけを縮小して描く。外部サムネイルはCORSで書き出せない場合がある。家族同期の写真参照が未解決、画像破損、メモリ不足、toBlob が null の場合も、同梱絵1枚・小さい解像度で再生成する。画像は1枚ずつ扱い、使い終えたオブジェクトURLを解放する。

iPhone Safariではタップ後に写真の読み込みやPNG生成を待つと、共有に必要なユーザー操作の効力が切れうる。**プレビュー時にPNGの File を生成し、完成後に共有ボタンを有効にする。** 設定変更時は古い File を破棄し、プレビューと共有対象を一致させる。HTTPSで navigator.canShare({files}) を確認し、タップ内で直ちに navigator.share({files}) を呼ぶ。キャンセルはプレビューに戻す。非対応・共有失敗時は同じPNGを通常の画像として開き、iPhoneでは長押し保存、Androidでは保存して投稿を選べるようにする。Instagramへの直接投稿や共有先一覧への表示は保証できない。

## 6. 流入の設計

スマホで見た画像のQRを同じ端末で読むのは手間がかかる。画像には「リピごち」の検索名、共有画面には投稿文に貼れるLPリンクのコピーを用意する。LPの最初に記録1件の見本と「最初の一皿を記録する」を置き、初回の記録導線へつなぐ。共通の流入タグだけで訪問を数え、家庭別リンクは作らない。共有シートの完了とSNSへの投稿成立は別なので、投稿数として報告しない。

## 7. 「5. 決まっていないこと」への答え

1. 「わたしの食卓」の見出し横に「レビュー」。月移動中に4週と暦月が入れ替わる混乱を避ける。
2. 各期間は主役一つ、数字一つ、次の操作一つ。内訳はⓘへ。
3. 魚を含むレシピ名など確認できた事実を出す。§67-2の人数・分量が不明な推定値を合算しない。
4. 同じ材料で別の一品を作った二つの記録を並べる。「挑戦した」という動機は推定しない。
5. 称号は見送る。好きな一皿を選ぶだけで個性が出る。
6. 一皿の大写しと「来年も食べたい」の一文。年間まとめの楽しさを、記録の少ない人にも渡せる。
7. 0件なら「この期間の記録はまだありません」と期間変更・記録への入口。1件なら一皿で完成、2件なら二択。半年・年も開放し、空白を未達扱いしない。
8. 同期家庭では「うちの食卓」。共通の記録は1回だけ数える。調理者は推測しない。見る人も閲覧でき、次の献立を変える操作は既存権限に従う。
9. 見本から最初の一皿へ直行。紹介特典は初版では設けない。
10. 暦年の一皿と縦画像を先行。週は既存レシートを活かし、4週以降の分析を待たずに出せる。

## 8. 最小で出すなら（年末に間に合わせる版）

2026年の実記録を日付で絞り、一皿を選び、同梱絵・記録日数・ロゴ入りの縦画像を生成する。プレビュー、画像共有、保存、LPリンクのコピーまでを一続きにする。写真・QR・ランキング・比較・栄養・作り手名・正方形版は後回し。過去データの移行や新しいサーバーは不要。

## 9. 気になるリスク

週1回の記録でも毎日料理しているかもしれない。「作れた割合」「連続が途切れた」は記録していない日を失敗に見せる。月・年をまたぐ週、うるう日、同日2件、デモだけ、回答が片方だけ、削除済みレシピを集計の確認例にする。編集や同期後は再計算し、過去に保存した画像と現在の記録が違ってもよい設計にする。

画像共有は今回の設計案で、実機動作は未検証。公開判断の前にiPhone Safari・ホーム画面から起動したPWA・Android Chromeで、共有先に**プレビューと同じPNGが届くこと**、キャンセル後の再試行、共有非対応時の保存とSNSへの手動添付まで試したい。
